# Verifying Optimistic Execution is Working

After the v0.7.0 upgrade, baseapp speculates `FinalizeBlock` in the background
during `ProcessProposal` instead of waiting until consensus locks the block in.
The feature is on by default in v0.7.0 and runs transparently. It's also
invisible to RPC clients (block headers and tx receipts look identical),
so the only way to confirm it's actually firing is from the validator host.

This doc gives you three checks, in order of cost:

1. **Free, always-on:** confirm no abort errors appear in the error stream
2. **One-shot diagnostic:** bump the log level for a few minutes and watch
   `OE started` / `OE finished` fire
3. **Throughput / latency check:** compare block-finalization timing to a
   v0.6 reference

You don't need to do all three. Pick the depth that matches how
paranoid you want to be about a feature that nominally just works.

## 1. Confirm no aborts (run any time)

If optimistic execution is malfunctioning, baseapp logs an `error`-level
message that says one of two things. Both are bad:

- `OE aborted due to hash mismatch` — speculation worked on one block hash,
  but consensus locked in a different one. Means we wasted CPU on the
  speculated work but it's not a correctness problem (the SDK falls back
  to a fresh `FinalizeBlock`). Should be rare. Possible causes: a
  re-proposal mid-round (proposer changed), or the chain is partitioning.
- `OE aborted due to test abort rate` — should never appear in production;
  it only fires if someone built a binary with `WithAbortRate(N)`.

To check the last hour of logs:

```bash
sudo journalctl -u epix.service --since '1 hour ago' \
  | grep -iE 'OE aborted|optimistic.*abort' \
  | head -50
```

Expected output on a healthy node: **nothing**. Zero lines.

If you want a longer window:

```bash
sudo journalctl -u epix.service --since '1 day ago' \
  | grep -iE 'OE aborted'
```

A handful of `hash mismatch` aborts per day is acceptable on a busy chain
with frequent proposer changes. Persistent or frequent aborts (more than
~1 per hour) suggest something's wrong: validator clock skew, network
partition, or a misconfigured proposer.

## 2. Confirm OE is firing (one-shot, restart required)

The "OE just ran" log lines are at `debug` level, so they're hidden by the
default `info` log level. To prove the speculation goroutine is actually
spinning up for each block, temporarily bump the log level and watch.

You have two options:

### Option A: Per-component debug for cosmos-sdk baseapp (preferred)

```bash
# Stop the service
sudo systemctl stop epix.service

# Add the baseapp debug filter. The exact syntax differs by deployment,
# but the typical place is the systemd unit file or the env file:
#
#   Environment=DAEMON_NAME=epixd
#   Environment=LOG_LEVEL=cosmossdk.io/baseapp:debug,*:info
#
# If you run epixd directly:
#   epixd start --log_level "cosmossdk.io/baseapp:debug,*:info"

sudo systemctl start epix.service

# Watch for 30-60 seconds — you should see OE started/finished every block
sudo journalctl -u epix.service -f --since '1 minute ago' \
  | grep -iE 'OE started|OE finished'
```

Expected output (one pair per block, sampled):

```
DBG OE started   height=1101234 hash=A1B2C3D4... time=2026-05-12T22:00:00Z
DBG OE finished  duration=18ms  height=1101234 hash=A1B2C3D4...
DBG OE started   height=1101235 hash=B2C3D4E5...
DBG OE finished  duration=22ms  height=1101235 hash=B2C3D4E5...
...
```

Two signals to check:

- **Both lines appear for every block.** If you see `OE started` but no
  matching `OE finished`, the speculation is being abandoned somewhere
  (possible bug or chain anomaly).
- **`duration` is shorter than the block interval.** Epix testnet runs
  ~5s blocks. Typical OE durations on a quiet block are 10-50ms; on a
  busy block they can climb but should stay well under 5000ms. If
  durations approach block interval, the chain is so loaded that
  speculation isn't gaining any latency.

When you're done observing, **revert the log level**. Debug-level logs
fill disks fast.

```bash
sudo systemctl stop epix.service
# remove the LOG_LEVEL override
sudo systemctl start epix.service
```

### Option B: Live debug without restart (if your unit supports it)

Some operators run with a writable log-level RPC. If yours does, you can
flip log levels without a restart. Most don't, and the restart is fine.

## 3. Compare consensus timing before/after (optional benchmark)

OE doesn't change *whether* blocks finalize correctly; it changes *when*
the validator has the result ready. The externally observable effect is
that `FinalizeBlock` arrives at the validator, and a result is already
cached, so the post-consensus latency before `Commit` drops.

A rough way to see this from CometBFT's side:

```bash
sudo journalctl -u epix.service --since '5 minutes ago' \
  | grep -iE 'committed state|finalized block' \
  | awk '{print $1, $2, $0}' \
  | tail -20
```

Compare against a v0.6 mainnet snapshot if you have one. Expect to see
the same block-production cadence (~5s on testnet, ~6s on mainnet) but
lower CPU pressure during the consensus phase — OE moves the heavy
execution work earlier in the round.

This is a soft signal. The hard signals are the absence of aborts
(section 1) and the presence of `OE started`/`OE finished` pairs
(section 2). If both look right, optimistic execution is working.

## What if something's wrong?

| Symptom | Likely cause |
|---|---|
| `OE aborted due to hash mismatch` recurring | Validator's view of the proposed block diverges from consensus. Check network connectivity to peers; if persistent, the proposer may be misbehaving. |
| `OE aborted due to test abort rate` | Wrong binary. You're running a debug build with `WithAbortRate(N)`. Rebuild from the v0.7.0 release tag. |
| No `OE started` lines after raising debug level | OE isn't enabled. Check `evmd/app.go` for `baseapp.SetOptimisticExecution()`. Should be present in the v0.7.0 codebase. |
| `OE finished` durations consistently approaching the block interval | The chain is so loaded that speculation isn't helping. Not a v0.7 bug — same situation would have produced very long `FinalizeBlock` on v0.6. Worth investigating the underlying load. |
| Service log shows neither aborts nor `OE` lines at all (with debug on) | Verify `LOG_LEVEL` filter syntax. The cosmos-sdk format is `<module>:<level>,*:<default>`. |

## Where to file issues

If you see something unexpected, capture:

- The last 200 lines of `journalctl -u epix.service`
- The output of `epixd status --node http://localhost:26657 | head -30`
- The output of `epixd version`

And open an issue at https://github.com/EpixZone/EpixChain/issues
