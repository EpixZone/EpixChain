# Validator Upgrade Guide: v0.7.0

This document tells validators what they need to do on the host running their
node for the v0.7.0 upgrade. It is not a developer migration guide — for
the technical changes inside the binary see
[`docs/migrations/v0.6.x_to_v0.7.0.md`](../migrations/v0.6.x_to_v0.7.0.md).

## Summary

The v0.7.0 upgrade requires one manual config edit on every node. The new
binary will refuse to start until it's done.

If you do nothing the upgrade height arrives, Cosmovisor swaps to the v0.7.0
binary, and `epixd` exits immediately with:

```
ERR configs mismatch error="EVM mempool enabled, but comet-bft has invalid config.toml:mempool.type (want 'app', got 'flood'): error in app.toml"
```

Your node will be stuck in a crashloop until you make the change below.

## What changed

v0.7.0 introduces the Krakatoa **application-side EVM mempool**. CometBFT no
longer queues incoming transactions itself; it hands them straight to `epixd`.
You need to tell CometBFT to do that by setting `mempool.type = "app"` in
`config.toml`.

The v0.6 default was `mempool.type = "flood"`, which used CometBFT's built-in
flood mempool. The two values are mutually exclusive and the v0.7.0 binary
validates the combination at startup.

## What to do

### Before the upgrade height (recommended)

You can do this any time before the upgrade height. The change is forward-
compatible: it only takes effect once the v0.7.0 binary is running, and the
v0.5.5 binary keeps working with the new value.

Edit `~/.epixd/config/config.toml`. Find the `[mempool]` section and change
the `type` line:

```diff
 [mempool]
- type = "flood"
+ type = "app"
```

Quick one-liner if you prefer:

```bash
sed -i 's/^type = "flood"$/type = "app"/' ~/.epixd/config/config.toml
```

Verify the change:

   ```bash
   grep -A1 '^\[mempool\]' ~/.epixd/config/config.toml | head -3
   ```

   You should see `type = "app"`.

Do not restart the node otherwise it will crash and you'll need to set it back to `flood`, restart, and then follow these instructions again.

### At the upgrade height (recovery)

If you missed the pre-upgrade window and your node is now crashlooping after
Cosmovisor swapped the binary:

1. Stop the service (Cosmovisor will keep restarting it otherwise):

   ```bash
   sudo systemctl stop epix.service
   ```

2. Apply the same `mempool.type` change as above.

3. Restart:

   ```bash
   sudo systemctl start epix.service
   ```

4. Tail the logs and confirm the node catches up:

   ```bash
   sudo journalctl -u epix.service -f
   ```

   You should see normal block production / sync logs, not the
   `configs mismatch` error.

## Other things to confirm

- **Binary staged via Cosmovisor.** The v0.7.0 binary must live at
  `~/.epixd/cosmovisor/upgrades/v0.7.0/bin/epixd` and be executable. If you
  use a different home directory, substitute accordingly.

- **Go runtime.** v0.7.0 is built with Go 1.25. If you compile from source on
  the validator host, make sure your `go` is recent enough.

- **`app.toml`.** No manual edit required. The v0.7.0 binary writes any new
  fields it expects the first time it runs.

- **No new ports.** No firewall changes required.

## Help

If your node fails to start with anything other than the documented
`configs mismatch` error, get help in the EpixZone Discord before forcing a
restart.
