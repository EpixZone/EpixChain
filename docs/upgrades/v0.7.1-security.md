# v0.7.1 Security Hotfix — Validator Runbook

**Severity:** Critical — remote fund theft
**Action required:** Replace the `epixd` binary. Do this today.
**Governance proposal:** None. **Coordinated halt:** None. **State migration:** None.

---

## What this fixes

The EVM state database allowed a transaction to write a stale cached balance
onto a **module account** (`bonded_tokens_pool`, `distribution`, `erc20`, and
friends). Module-account funds are moved by precompiles through the bank
keeper, so those balances are not tracked by the EVM journal. A contract that
touches a module account and calls a precompile in the same transaction could
commit a pre-call balance over the precompile's bank-side bookkeeping, and
spend the same funds twice.

This is the same bug class as the ICS20 advisory
([GHSA-54gx-3cgr-7mfm][adv]) — inconsistent state across nested EVM execution —
reached through a different door.

**Epix is reachable:** the staking precompile (`0x…0800`) is in
`active_static_precompiles`, and `access_control` is `PERMISSIONLESS` for both
create and call, so any funded account can deploy the contract needed to
trigger it.

Upstream shipped this as `cosmos/evm` **v0.7.1** (commit `b8d5ed7b`). Mainnet
runs `v0.7.0-5-g6c901bac`, which predates it.

[adv]: https://github.com/cosmos/evm/security/advisories/GHSA-54gx-3cgr-7mfm

### Behaviour change to be aware of

Rejecting the write is unconditional for module accounts, including a write
that leaves the balance unchanged. One consequence: **a module account can no
longer deploy a contract through `CallEVM`**, because contract creation bumps
the sender's nonce and `SetAccount` writes nonce and balance together.

Nothing in Epix does this — `x/erc20` only *calls* already-deployed contracts
from the module account, and no production code path deploys from one.
Upstream reached the same conclusion and moved its own tests to an EOA deployer
([cosmos/evm#1243][pr]) rather than relaxing the guard. Ordinary calls from
module accounts, including the `x/erc20` transfer path, are unaffected.

[pr]: https://github.com/cosmos/evm/pull/1243

### What this does *not* fix

The ICS20 advisory that prompted this review is **already patched** on mainnet —
it shipped in v0.7.0. No action needed there.

## Why there is no governance proposal

A `MsgSoftwareUpgrade` plan requires a voting period we do not have, and it
works by **halting the chain** at the upgrade height — which is the wrong shape
for a fix whose entire purpose is to stop an attack that can land right now.

This patch changes no store keys, runs no migration, and registers no upgrade
handler. It is a pure binary swap. Nothing about it needs to be coordinated
on-chain.

> Do **not** add this to `RegisterUpgradeHandlers`. Doing so would convert a
> drop-in binary replacement into a gov-gated chain halt.

---

## Is a rolling upgrade consensus-safe?

Yes, with one thing to understand.

The patch changes the outcome of a transaction **only** when that transaction
writes a module-account balance through the EVM journal. No organic traffic
does this: fee collection uses `SendCoinsFromAccountToModuleVirtual` on the
bank keeper, and precompiles operate on bank balances directly — neither goes
through the patched path. Patched and unpatched nodes therefore produce
identical app hashes for all normal traffic, and validators can restart in any
order, at any time, with no coordination.

The one divergence case is an actual exploit attempt during the rollout window.
There, patched nodes reject the transaction and unpatched nodes accept it, so
the two groups compute different app hashes. What happens next depends only on
how much voting power has upgraded:

| Patched voting power | If someone attacks mid-rollout |
| --- | --- |
| **< 1/3** | The exploit finalizes. Funds are stolen; patched nodes fork off. |
| **> 1/3** | The exploit **cannot finalize** — the block never reaches 2/3. The chain halts instead of paying out. |
| **100%** | The exploit reverts as a failed transaction. Business as usual. |

So the rollout has a fail-safe point rather than a cliff: **crossing 1/3 of
voting power converts the failure mode from "funds stolen" to "chain pauses."**
A pause is recoverable in an hour; a drain is not. Past 2/3 the risk of a stall
is gone too, and at 100% you are simply patched.

This is why the fix is **not** height-gated. A height gate would make the
rollout perfectly deterministic, but it would also keep the hole open until the
activation height *and* publish that deadline to anyone reading the commit —
handing an attacker both a target and a countdown. Given the advisory is
already public, closing the hole as each validator restarts is strictly better.

**Operational consequence:** get to 1/3 as fast as you can, then to 2/3. Do not
wait for a synchronized window, and do not wait for stragglers before starting.

| `11D3AEB40FA9E3C7` | 603,772,057 | 7.21% |
| `B9E1469CE6F33407` | 583,457,149 | 6.97% |

The largest validator holds **34.46%** — above 1/3, below 1/2, and well below
2/3. Two consequences follow, and they pull in opposite directions:

- **Patching that one validator is enough to make theft impossible.** At 34.46%
  it can withhold its signature from any block carrying the exploit, and the
  remaining 65.54% cannot reach the 2/3 needed to finalize. The attack stops
  being profitable the moment that node restarts on the patched binary, with
  every other validator still unpatched.
- **It cannot carry the chain by itself.** 34.46% is a blocking third, not a
  majority — producing blocks still needs 2/3 total, so the other validators
  must be online and agreeing. Patching it protects funds; it does not make
  the rest of the rollout optional.

Recheck these numbers before relying on them; voting power moves.

## If the chain is currently paused

A halt is the best possible moment to apply this: patch before resuming and the
network never runs vulnerable again, so the exposure window is zero rather than
"however long the rollout takes."

If the chain is stopped because a validator holding a blocking third is offline,
the sequence is:

1. Build and install the patched binary on that validator **while it is still
   down** (steps below).
2. Start it. The chain resumes as soon as 2/3 of voting power is online and
   agreeing — the patched node agrees with unpatched peers on all organic
   traffic, so this needs no coordination with anyone else.
3. Theft is now off the table. Roll the remaining validators at a normal pace
   to restore full liveness safety.

Do not restart on the old binary first "to get blocks moving" and patch after.
That reopens the window for no benefit — the patched binary rejoins exactly as
readily as the unpatched one.

## Procedure

Per validator, roughly 10 minutes, no coordination with anyone else.

```bash
# 1. Build
git fetch origin
git checkout v0.7.1
make build          # or: make install

# 2. Confirm you built the right thing
./build/epixd version --long | grep -E 'version|commit'

# 3. Swap and restart
sudo systemctl stop epixd
sudo cp ./build/epixd $(which epixd)
sudo systemctl start epixd

# 4. Watch it rejoin
journalctl -u epixd -f | grep -E 'height|APP HASH|panic'
```

Cosmovisor users: drop the binary in
`~/.epixd/cosmovisor/current/bin/` and restart the service. Do **not** create
an `upgrades/` directory for this — there is no upgrade plan to trigger.

### Verify you are patched

```bash
epixd version --long | grep commit   # expect the v0.7.1 commit
```

Chain-side, confirm you are still in consensus with the network:

```bash
curl -s localhost:26657/status | jq '.result.sync_info.catching_up'   # false
curl -s localhost:26657/status | jq '.result.sync_info.latest_block_height'
```

Compare that height against a public node
(`https://rpc.epix.zone/status`). If your node stops advancing and the logs show
an app-hash mismatch, **do not roll back** — report it in the validator channel
first. That signal is meaningful and rolling back destroys it.

## If the rollout stalls

If voting power on the patched binary is not moving and you cannot reach enough
validators:

- **Disabling precompiles by governance is not a substitute.** The vulnerable
  primitive is reachable through any precompile that performs bank operations
  on a module account, so removing the staking precompile from
  `active_static_precompiles` narrows the surface without closing it — and it
  still costs a full voting period.
- The effective lever is validator outreach, not an on-chain action. Prioritize
  the largest operators until cumulative patched power clears 1/3.

## Follow-up (not urgent, not part of this hotfix)

The full upstream sync to `cosmos/evm` v0.7.1 sits on
`upgrade/sync-upstream-v0.7.1`. It carries 26 upstream commits, several of them
consensus-affecting beyond this one fix — EVM signature verification in the ante
handler, mempool base-fee admission, statedb locked-balance snapshotting, and
the erc20 IBC middleware. That set is **not** appropriate for an uncoordinated
rolling swap: unlike this hotfix, those changes alter the outcome of ordinary
transactions, so a partial rollout would fork the chain under normal traffic.

Land it the usual way, as a governance-scheduled upgrade, once this hotfix is
out and the network is safe.
